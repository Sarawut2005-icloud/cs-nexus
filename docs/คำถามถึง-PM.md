### 0. ยืนยันตัวตน: Gateway SSO หรือ Supabase Auth — ข้อไหนคือของจริง

**เร่งด่วนที่สุด กระทบมากกว่าทุกข้อด้านล่าง**

จากการแกะ `csmju-aie-system.rar` (รายละเอียดเต็มอยู่ที่
`docs/แกะ-csmju-aie-system.md`) พบว่า **AIE 3 ใช้ Supabase Auth และมีหน้า
login ของตัวเอง** ส่วนหน้าบ้านก็คุยกับฐานข้อมูลตรงผ่าน Prisma ใน Next.js

แต่เราถูกบอกว่า **ห้าม** ทำทั้งสามอย่างนั้น และเราประกาศใน `subsystem.yaml`
ไปแล้วว่าไม่ทำ ตอนนี้จึงมีสองมาตรฐานอยู่ในระบบเดียวกัน

ขอ PM ชี้ขาด เพราะผลต่างกันคนละขั้ว:

- **ถ้าเป็น Gateway SSO** → AIE 3 ต้องรื้อส่วนล็อกอินออก ส่วนเราเดินต่อได้เลย
- **ถ้าเป็น Supabase Auth** → **เราต้องรื้อสถาปัตยกรรมทั้งระบบ** และคำถาม
  ข้อ 1–3 ด้านล่างก็ไม่เกี่ยวอีกต่อไปทั้งหมด

ทุกวันที่ยังไม่มีคำตอบ คืองานที่อาจต้องทิ้งเพิ่มขึ้นเรื่อย ๆ

### 0.1 ฐานข้อมูล: แยกตามระบบย่อย หรือใช้ร่วมกัน

ใน monorepo มี `prisma/schema.prisma` **หนึ่งตัวที่ราก** และเนื้อในเป็น

อ่านได้สองแบบ:

- **(ก)** ตั้งใจให้เป็นฐานข้อมูลกลางที่ทุกระบบย่อยใช้ร่วมกัน
- **(ข)** เป็นแค่ของ AIE 3 ที่วางผิดที่ เพราะตอนนั้นยังมีระบบเดียว

ถ้าเป็น (ก) ขัดกับ Database-per-Subsystem (หน้า 10) และ**เราต้องรื้อ schema
ทั้งก้อน** ขอคำตอบเป็นลายลักษณ์อักษรก่อนเริ่มแก้

### 1. API Gateway proxy WebSocket ให้ไหม และแนบ header ตอน handshake ไหม

**ทำไมถึงสำคัญที่สุด:** ฟีเจอร์เรียลไทม์ทั้งหมดของระบบนี้อยู่บน WebSocket —
แชท · การแจ้งเตือน · สายเรียกเข้า · ห้องเสียง · สถานะออนไลน์ ถ้าคำตอบเปลี่ยน
สถาปัตยกรรมส่วนนี้ต้องรื้อใหม่

**ตอนนี้ทำไว้ยังไง:** เพราะยังไม่รู้คำตอบ เราเลยทำกลไก "ตั๋ว" ไว้ก่อน —
client ขอตั๋วทาง REST (ผ่าน Gateway จึงมี header) แล้วเอาตั๋วไปแลกตอนต่อ socket
ตั๋วสุ่ม ใช้ได้ครั้งเดียว หมดอายุ 60 วินาที

**สิ่งที่อยากรู้:**
- Gateway proxy โพรโทคอล WebSocket (`Upgrade: websocket`) ให้ไหม
- ถ้าได้ แนบ `X-User-Id` / `X-Layer1-Role` / `X-Faculty` มาตอน handshake ด้วยไหม
  → ถ้าใช่ เราจะ**ตัดกลไกตั๋วทิ้ง** แล้วอ่าน header ตรง ๆ ซึ่งง่ายและปลอดภัยกว่า
- ถ้าไม่ proxy ให้ ระบบย่อยควรเปิด WebSocket ให้ต่อตรงได้ไหม แล้วยืนยันตัวตนด้วยวิธีไหน

---

### 2. Gateway พิสูจน์ตัวเองกับระบบย่อยยังไง

**ทำไมถึงสำคัญ:** Blueprint หน้า 9 บังคับให้ระบบย่อย **เชื่อ header** และห้าม
ตรวจลายเซ็น JWT เอง ซึ่งถูกต้อง — แต่การเชื่อ header จะปลอดภัยก็ต่อเมื่อ
**ไม่มีใครยิงเข้า backend ได้โดยตรง**

เราทดสอบแล้วว่าถ้า backend เปิดรับจากอินเทอร์เน็ตโดยไม่มีอะไรกั้น การส่ง
`X-User-Id: <ชื่อใครก็ได้>` ทำให้กลายเป็นคนนั้นได้ทันที (อ่านแชทส่วนตัว
ลบโพสต์ เปลี่ยนสิทธิ์คนอื่น) ตอนนี้เราทำให้ระบบ**ไม่ยอมบูต**ถ้าไม่ได้ตั้งค่านี้

**สิ่งที่อยากรู้:**
- Gateway ส่ง shared secret มากับทุกคำขอไหม ชื่อ header ว่าอะไร ค่าอะไร
  (เราเตรียมรับไว้ที่ `x-gateway-secret` แต่เปลี่ยนตามที่ PM กำหนดได้)
- หรือใช้วิธีอื่น เช่น mTLS / IP allowlist / private network
- ค่านี้หมุนบ่อยแค่ไหน และแจ้งระบบย่อยทางไหน

## ข. สัญญาของ Core ที่เราเดาไว้ ขอยืนยัน

### 4. รูปแบบ user_profile_api

Blueprint หน้า 10 กำหนดว่า Core เป็นแหล่งความจริงของชื่อและคณะ เราจึงต้องดึง
ชื่อที่แสดงผลจาก Core **ตอนนี้เดาไว้แบบนี้:**

```
GET {CSMJU_CORE_API_URL}/api/v1/users/{username}
→ { "data": { "display_name": "...", "avatar_url": "..." } }
```

ขอทราบรูปแบบจริง: path · ชื่อฟิลด์ · วิธียืนยันตัวตนตอนเรียก (client credential?)
· มี endpoint ดึงหลายคนทีเดียว (batch) ไหม — ถ้าไม่มี การเรนเดอร์ฟีด 20 รายการ
จะต้องยิง 20 ครั้ง

> ตอนนี้ถ้า Core ยังไม่มีให้เรียก ระบบจะ fallback ไปแสดง `username` แทน
> ซึ่งใช้งานได้แต่ผู้ใช้จะเห็นรหัสนักศึกษาแทนชื่อจริง

---

### 5. Core มี endpoint ค้นหาคนไหม

ตอนนี้ช่องค้นหาคนของเราค้นได้**เฉพาะคนที่เคยถูกซิงก์ชื่อมาแล้ว** — คนที่ยังไม่เคย
เข้าใช้ระบบย่อยนี้จะหาด้วยชื่อจริงไม่เจอ (หาด้วย username เจอ)

อาการที่ผู้ใช้เจอ: อยากทักเพื่อนที่ยังไม่เคยเข้าระบบนี้ แต่ค้นชื่อไม่เจอ

ถ้า Core มี endpoint ค้นคน เราจะเรียกต่อแล้วปัญหานี้หายไปเลย

## ค. ขอคำวินิจฉัยเรื่องมาตรฐาน

### 6. แคชชื่อที่แสดงผล ผ่านมาตรฐานหน้า 10 ไหม

หน้า 10 ห้ามเก็บข้อมูลของ Core ซ้ำซ้อน เราตีความว่า **"แคชที่มีวันหมดอายุและ
ไม่ใช่แหล่งความจริง" ต่างจาก "การเก็บซ้ำ"** จึงทำตาราง `profile_cache`
เก็บ `display_name` + `avatar_url` พร้อม `synced_at` TTL 6 ชั่วโมง

เหตุผล: ถ้าไม่แคช การเรนเดอร์ฟีดหนึ่งหน้าต้องยิง Core 20 ครั้ง

**ขอ PM ยืนยันว่าการตีความนี้ผ่าน** ถ้าไม่ผ่านเราจะเอาออกและเรียก Core ทุกครั้ง
(ช้าลงมาก) หรือให้หน้าบ้านเรียก Core เอง

---

### 7. `bio` และรูปปก นับเป็น Local Data ไหม

เส้นที่เรายึด: **Core เป็นเจ้าของ "ตัวตน"** (ชื่อจริง คณะ อีเมล รูปโปรไฟล์)
ส่วนข้อความแนะนำตัวที่ผู้ใช้เขียน**เพื่อชุมชนนี้โดยเฉพาะ** กับรูปปกของหน้าโปรไฟล์
ในระบบย่อยนี้ เป็น **"เนื้อหาที่ผู้ใช้สร้าง"** เหมือนโพสต์หรือคอมเมนต์ จึงเก็บที่นี่

เราไม่ได้เก็บชื่อจริงหรือรูปโปรไฟล์ลงฐานข้อมูลเด็ดขาด

**ขอ PM ยืนยันว่าเส้นแบ่งนี้ถูกต้อง**

### 9. เราย้ายเข้า monorepo เมื่อไหร่ และย้ายแบบไหน

จากการแกะไฟล์ รู้แล้วว่าช่องของเราคือ `apps/aie4-social-reels/` ซึ่งตอนนี้
**ยังว่างเปล่า** (เช่นเดียวกับ `aie1-canva`, `aie2-line-hub` และ `shared/`)

ที่ยังไม่รู้คือวิธีย้าย ขอ PM เลือกหนึ่งข้อ:

- **ย้ายโค้ดเข้าไปตรง ๆ** — ง่ายที่สุด แต่ทิ้งประวัติ git ของเรา
- **ผูกเป็น git submodule** — เก็บประวัติไว้ครบ แต่คนอื่นต้องรู้จักคำสั่ง submodule
- **คงเป็น repo แยกไปก่อน** แล้วค่อยรวมทีหลัง

ข้อสังเกต: AIE 3 ในไฟล์นั้นมีโฟลเดอร์ `.git` ของตัวเองซ้อนอยู่ข้างใน ซึ่งแปลว่า
ตอนนี้เป็นแค่การก็อปโฟลเดอร์มาวาง ยังไม่ได้ตัดสินใจเรื่องนี้จริงจัง

ฝั่งเราพร้อมย้ายทั้งสามแบบ สำรวจแล้วว่ากระทบแค่ 5 ไฟล์ตั้งค่า
(`render.yaml`, Vercel Root Directory, `subsystem.yaml`, `DEPLOY.md`,
`.githooks`) **ไม่ต้องแก้ไฟล์ source สักไฟล์** เพราะใช้เส้นทางสัมพัทธ์กับ
alias `@/` อยู่แล้ว

## จ. แจ้งให้ทราบ (ไม่ต้องตอบ)

- **พบรหัสผ่านจริงหลุดในไฟล์ที่แชร์กันในทีม** — `csmju-aie-system.rar`
  มี `apps/aie3-coding-game/.env.local` ติดมาด้วย ข้างในมี `DATABASE_URL`
  พร้อมรหัสผ่าน และกุญแจ Supabase **แจ้ง AIE 3 ให้หมุนรหัสใหม่ทันที**
  และขอให้ทีมเลิกแชร์โค้ดด้วยการบีบอัดทั้งโฟลเดอร์ เพราะมันกวาด `.env`
  ติดไปเสมอ ต่างจาก git ที่มี `.gitignore` กันไว้อยู่แล้ว

- **ยังไม่มี TURN server** คนที่อยู่หลัง NAT แบบเจาะไม่ได้ (พบบ่อยในเน็ตมหาลัย
  และเน็ตมือถือ) จะใช้ห้องเสียงไม่ได้ ระบบมีปุ่มให้ผู้ใช้ตรวจเครือข่ายตัวเองก่อนโทร
  ถ้าคณะมีเครื่องให้รัน `coturn` ได้จะแก้ปัญหานี้ทันทีโดยไม่มีค่าใช้จ่าย

- **ตอนนี้วางแผนขึ้นชั้นใช้ฟรี** (Vercel + Render + Supabase) ซึ่งไม่มี SLA และ
  เซิร์ฟเวอร์จะหลับเมื่อไม่มีคนใช้ 15 นาที เหมาะกับการเดโมและงานเรียน
  ถ้าจะเปิดใช้จริงทั้งคณะ ต้องคุยเรื่องที่วางระบบ

- **`openapi.json` พร้อมแล้ว** 67 path · 65 schema และมี CI ตรวจว่าตรงกับโค้ด
  เสมอ ระบบย่อยอื่นที่ต้องคุยกับเราอ่านไฟล์นี้ได้เลย

## ฉ. สิ่งที่ PL ตัดสินเองได้ (ไม่ต้องรบกวน PM)

จดไว้กันลืม ไม่ต้องถาม:

- เพิ่ม `peer_username` และ `i_have_replied` ใน `ChannelResponseDto` ของเราเอง
  (ตอนนี้หน้าบ้านเดาคู่สนทนาจากชื่อห้อง ซึ่งเปราะ)
- เปลี่ยนฟีดและแชทเป็น cursor pagination (ตอนนี้ใช้ offset ซึ่งทำให้ข้อความ
  ซ้ำหรือหายตอนเลื่อนย้อนหลังขณะมีคนโพสต์ใหม่)
- ตัวเก็บกวาดไฟล์ยังไม่มี lock — จำเป็นเมื่อสเกลเป็นหลาย instance เท่านั้น
- ระบบยังขาด PDPA cookie consent ซึ่งจำเป็นตามกฎหมายไทยถ้าเปิดใช้จริง
