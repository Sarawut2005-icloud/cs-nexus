## 3. สิ่งที่ **ใช้ไม่ได้** — และเหตุผลว่าทำไมห้ามเอามาใช้

### 3.1 `prisma/schema.prisma` ที่รากไม่ใช่ schema กลาง

มันคือ schema ของเกม AIE 3 ล้วน ๆ:

```prisma
model User {
  id    String @id @default(uuid())
  email String @unique     // ← ปัญหาอยู่ตรงนี้
  role  Role   @default(STUDENT)
}
model Problem    { ... }   // โจทย์ปัญหาในเกม
model Submission { ... }   // คำตอบที่ส่ง
```

**ถ้าเราต่อเข้าฐานข้อมูลเดียวกันนี้ จะผิดสองข้อพร้อมกัน:**

1. **ผิด Database-per-Subsystem (Blueprint หน้า 10)** — `Problem` กับ
   `Submission` เป็นข้อมูลของ AIE 3 เราไม่ควรมองเห็นมันด้วยซ้ำ
2. **ผิดข้อห้ามเก็บตัวตนซ้ำ** — `User.email` คืออีเมลจริงของนักศึกษา
   `subsystem.yaml` ของเราประกาศไว้ชัดว่า `never_stored: [layer1_role,
   faculty, email, ...]` และเราใช้ `username` เป็นคีย์เดียวทั้งระบบ

schema ของเราเอง (`backend/prisma/schema.prisma`) ทำถูกอยู่แล้ว
**ไม่ต้องแก้ตาม**

### 3.2 วิธียืนยันตัวตนของ AIE 3 ขัดกับข้อห้ามที่เราถูกสั่งให้ทำตาม

AIE 3 ใช้ **Supabase Auth ตรง ๆ**:

```ts
// apps/aie3-coding-game/src/utils/supabase/server.ts
import { createServerClient } from '@supabase/ssr'
const cookieStore = await cookies()
```

และหน้าบ้าน **คุยกับฐานข้อมูลตรง** ผ่าน Prisma ใน Next.js
(`src/lib/prisma.ts` อยู่ในโปรเจกต์ Next ไม่มีหลังบ้านแยก)

เทียบกับสิ่งที่ `subsystem.yaml` ของเราประกาศไว้กับ PM:

| ข้อ | เราประกาศไว้ | AIE 3 ทำ |
| --- | --- | --- |
| มีหน้า login ของตัวเอง | `false` | ใช้ Supabase Auth = มี |
| หน้าบ้านแตะฐานข้อมูล | `false` | แตะตรง |
| เก็บตัวตนซ้ำกับ Core | `false` | เก็บ email ในตาราง User |

**ถ้าผม "ปรับให้เหมือนเขา" ตามที่ขอ ผมจะต้องรื้อสถาปัตยกรรมเราทิ้ง
แล้วละเมิดข้อห้ามสามข้อที่เราเซ็นชื่อไว้กับ PM** — ผมจึงไม่ทำ
และขอให้ถาม PM ก่อนว่าใครถูก (ดูข้อ 5)

ไม่ได้แปลว่า AIE 3 ทำผิด — อาจเป็นเพราะเขายังไม่ได้ต่อ Gateway เหมือนกัน
แล้วใช้ Supabase ไปพลางก่อน ซึ่งเป็นทางที่สมเหตุสมผลถ้าไม่มีใครบอกว่าห้าม

### 3.3 การตั้งค่า Prisma ที่รากเป็นแบบเก่ากว่าของเรา

```prisma
generator client {
  provider = "prisma-client-js"   // ← generator รุ่นเดิม
}
```

Prisma 7 ใช้ `prisma-client` เป็นค่าเริ่มต้นแล้ว `prisma-client-js`
ยังใช้ได้แต่เป็นทางเข้ากันได้ย้อนหลัง ของเราใช้ `prisma-client` + driver
adapter ซึ่งเป็นทางที่ Prisma 7 แนะนำ — **เราใหม่กว่า ไม่ต้องถอยตาม**

## 4. เรื่องความปลอดภัยที่ต้องบอก — ในไฟล์มีรหัสจริง

ไฟล์ `apps/aie3-coding-game/.env.local` **ติดมาในไฟล์บีบอัดด้วย** ข้างในมี:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `DATABASE_URL` ← สายเชื่อมฐานข้อมูลพร้อมรหัสผ่าน
- `DIRECT_URL`

ผมไม่ได้เปิดอ่านค่าและไม่ได้บันทึกไว้ที่ไหน แต่**คนอื่นที่ได้ไฟล์นี้ไปอ่านได้ทันที**

**สิ่งที่ควรทำ:**

1. บอก AIE 3 ให้ **เปลี่ยนรหัสฐานข้อมูลและหมุนกุญแจ Supabase ใหม่**
   เพราะถือว่ารั่วแล้วนับจากวินาทีที่ไฟล์ถูกส่งต่อ
2. อย่าส่งไฟล์บีบอัดนี้ต่อให้ใครอีก
3. บอกทีมว่าเวลาแชร์โค้ด ให้ใช้ git (ซึ่ง `.gitignore` กัน `.env` อยู่แล้ว)
   ไม่ใช่บีบอัดทั้งโฟลเดอร์ — การบีบอัดทั้งโฟลเดอร์จะกวาด `.env` ติดไปเสมอ

## 5. คำถามที่ต้องถาม PM (เพิ่มจากที่มีอยู่)

### ข้อ 10 — ฐานข้อมูล: แยกตามระบบย่อย หรือใช้ร่วมกัน

ใน monorepo มี `prisma/schema.prisma` **หนึ่งตัวที่ราก** ซึ่งอ่านได้สองแบบ:

- **(ก)** ตั้งใจให้เป็นฐานข้อมูลกลางที่ทุกระบบย่อยใช้ร่วมกัน
- **(ข)** เป็นแค่ของ AIE 3 ที่วางผิดที่ เพราะตอนนั้นยังมีระบบเดียว

**ถ้าคำตอบคือ (ก) เราต้องรื้อ schema ทั้งก้อน** ซึ่งกระทบทุกโมดูล
ขอคำตอบเป็นลายลักษณ์อักษรก่อนเริ่ม

### ข้อ 11 — ยืนยันตัวตน: Gateway SSO หรือ Supabase Auth

AIE 3 ใช้ Supabase Auth และมีหน้า login ของตัวเอง ส่วนเราถูกบอกว่า
**ห้าม** ทำทั้งสองอย่าง ตอนนี้จึงมีสองมาตรฐานอยู่ในระบบเดียวกัน

ขอให้ PM ชี้ขาดว่าอันไหนคือของจริง เพราะ:

- ถ้าเป็น Gateway SSO → AIE 3 ต้องรื้อส่วนล็อกอินออก
- ถ้าเป็น Supabase Auth → **เราต้องรื้อสถาปัตยกรรมทั้งระบบ** และคำตอบ
  ข้อ 1–3 ในเอกสารคำถามเดิมก็ไม่เกี่ยวอีกต่อไป

นี่เป็นคำถามที่กระทบงานมากที่สุดในตอนนี้ **มากกว่าเรื่อง WebSocket**

### ข้อ 9 (ปรับใหม่) — เราย้ายเข้า monorepo เมื่อไหร่ และย้ายแบบไหน

รู้แล้วว่าช่องของเราคือ `apps/aie4-social-reels/` แต่ยังไม่รู้ว่า:

- ให้ย้ายโค้ดเข้าไปตรง ๆ (ทิ้งประวัติ git ของเรา) หรือ
- ให้ผูกเป็น git submodule (เก็บประวัติไว้) หรือ
- ให้คงเป็น repo แยกไปก่อน แล้วค่อยรวมทีหลัง

AIE 3 ในไฟล์นี้มีโฟลเดอร์ `.git` ของตัวเองอยู่ข้างใน ซึ่งแปลว่าตอนนี้
**ยังไม่มีใครตัดสินใจจริงจัง** มันเป็นแค่การก็อปโฟลเดอร์มาวาง

## 6. ถ้า PM ให้ย้ายเข้า monorepo — สิ่งที่ต้องแก้

ยังไม่ได้ทำ รอคำตอบข้อ 9 ก่อน แต่สำรวจไว้แล้วว่ากระทบตรงไหนบ้าง
**ทั้งหมดเป็นเรื่องเส้นทาง ไม่มีโค้ดที่ต้องเขียนใหม่:**

| ไฟล์ | แก้อะไร |
| --- | --- |
| `render.yaml` | `rootDir: backend` → `apps/aie4-social-reels/backend` |
| Vercel | ตั้ง Root Directory เป็น `apps/aie4-social-reels` |
| `subsystem.yaml` | แก้ `repo:` ให้ชี้ที่อยู่ใหม่ |
| `DEPLOY.md` | แก้ขั้นตอนที่อ้างโฟลเดอร์ราก |
| `.githooks` | `core.hooksPath` เป็นค่าต่อ repo — ถ้ารวม repo ต้องย้ายไปตั้งที่ราก monorepo |

โค้ดในโปรเจกต์ใช้เส้นทางแบบสัมพัทธ์กับ alias `@/` ทั้งหมดอยู่แล้ว
จึงไม่ต้องแก้ไฟล์ source สักไฟล์

   คือความเสี่ยงว่าจะต้องรื้องานทิ้ง

   PDPA cookie consent ซึ่งจบในตัวและเป็นข้อบังคับทางกฎหมายไทยอยู่แล้ว
